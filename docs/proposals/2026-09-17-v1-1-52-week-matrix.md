## Key implementation detail by changed block

### Weeks 9–13 — dual-relational foundation

Do not teach MySQL and PostgreSQL as two independent SQL courses.

Teach:

```text
relational model
SQL
indexes
query plans
transactions
MVCC
locks
deadlocks
```

then require engine-specific evidence in both.

Recommended Project split:

```text
Project A → MySQL
Project B → PostgreSQL
```

This keeps both databases active after the initial data phase.

### Week 14 — gRPC conceptual entry

Keep HTTP/REST/OpenAPI dominant.

Allocate a bounded block to:

```text
IDL / .proto
service / method
message schema
unary RPC
streaming concept
generated clients/servers
deadline/error semantics
REST vs gRPC decision
```

No production microservice decomposition is required.

### Week 24 — Python/FastAPI secondary core

Week outcome:

> Build, test, debug, and explain one bounded Python/FastAPI backend service and connect it to the existing platform without turning the project into unnecessary microservices.

Suggested 12h internal allocation:

| Block | Hours |
|---|---:|
| Python typing/project/runtime basics | 2 |
| FastAPI + Pydantic request/response model | 2 |
| dependency boundaries + testing | 2 |
| async/concurrency concepts relevant to API work | 1.5 |
| PostgreSQL/HTTP integration | 1 |
| Protobuf/gRPC practical server/client | 1.5 |
| project evidence + assessment + English explanation | 2 |
| **Total** | **12** |

The service boundary must be justified by an ADR.

### Week 27 — DynamoDB supporting lab

Suggested scope:

```text
access patterns first
partition key
sort key
item collections
GSI
strong vs eventual read concepts
hot partition risk
RDS vs DynamoDB decision
```

Do not teach DynamoDB as relational tables without joins.

### Week 32 — Kubernetes supporting lab

Suggested 12h balance:

| Scope | Hours |
|---|---:|
| resilience/timeouts/retries | 2 |
| Deployment + Service | 2 |
| ConfigMap/Secret concepts | 1 |
| readiness/liveness + rollout | 2 |
| requests/limits + application behavior | 1 |
| troubleshooting with logs/events | 2 |
| Helm + Argo/GitOps exposure | 1 |
| assessment/English explanation | 1 |

Cluster administration remains out of scope.

### Week 34 — MongoDB + distributed-data/NoSQL week

Suggested 12h internal allocation:

| Scope | Hours |
|---|---:|
| document model + access patterns | 2 |
| embed vs reference + schema validation | 1.5 |
| indexes + aggregation/query evidence | 1.5 |
| replica/read-write concern concepts | 1 |
| sharding/shard-key/hotspot reasoning | 1.5 |
| DynamoDB comparison | 1 |
| Cassandra + OpenSearch boundary exposure | 0.5 |
| system-design/data-store selection simulation | 2 |
| assessment/English | 1 |
| **Total** | **12** |

The practical must compare MongoDB with PostgreSQL/JSONB before deciding MongoDB is justified.

### Weeks 36–40 — Python reinforcement through AI

Python should become the default reference implementation for:

- structured-output service;
- tool-calling orchestration;
- RAG/retrieval pipeline;
- eval harness.

The learner should still be able to integrate those capabilities from PHP/Laravel.

This reinforces Python without creating new weeks.

### Week 41 — polyglot backend literacy

Suggested split:

```text
6h backend polyglot exposure
6h Big O + arrays/strings/hash maps
```

Polyglot exposure:

| Ecosystem | Expected evidence |
|---|---|
| Go | identify package/module, handler/service/client, context/error flow, tests; make one small safe patch |
| Java/Spring | identify controller/service/repository/DI/config/transaction/test path; make one small safe patch |
| TypeScript/Node | identify typing/async/service/HTTP/config/test path; make one small safe patch |

No new large projects are created.

### Weeks 47–52 — market campaign

Do not add fixed new technology load.

Use real active-pipeline signals to deepen:

- Go;
- Java/Spring;
- TypeScript/Node;
- PostgreSQL;
- MongoDB;
- DynamoDB;
- Kubernetes;
- gRPC;

only when relevant to an active target role or repeated market signal.
